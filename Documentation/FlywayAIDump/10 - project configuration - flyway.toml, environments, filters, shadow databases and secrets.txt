## 1. How configuration is layered

| Layer | Where | Use for |
|---|---|---|
| `flyway.toml` | Project root, committed | Shared settings, comparison settings, and every environment: development and shadow, plus the deployed ones through `${env.X}` (section 6) |
| `flyway.user.toml` | Project root, git-ignored | One developer's own connection details |
| `ci/<environment>.toml` | Optional. Committed, loaded with `-configFiles` | One deployed environment each, when you want a job to see only its own environment (section 6) |
| Environment variables | Runner, job step, shell | Secrets and per-run values |
| Command-line parameters | The command | One-off overrides |

Redgate's precedence page lists command-line arguments first, then environment variables, standard input, configuration files and defaults.

Flyway looks for TOML files in four folders, and later ones win: the install folder's `conf/`, the user home folder, the folder Flyway is run from, then the working directory. In each folder `flyway.user.toml` overrides `flyway.toml`.

`-configFiles` (environment variable `FLYWAY_CONFIG_FILES`) loads files in addition to those loaded automatically, with relative paths resolved against the working directory. Redgate's configFiles parameter page says so, and a test run confirmed it: with `-configFiles` naming another file, Flyway still found an environment defined only in the working directory's `flyway.toml`. Redgate's precedence page is worded as if the named files replace the automatic ones. Prove it with your own run on your pinned engine before a pipeline depends on it: check that a command with `-configFiles` still finds an environment that exists only in `flyway.toml`. Don't prefix `-configFiles` or `workingDirectory` paths with `filesystem:`; that prefix belongs on `locations` only.

If Flyway finds a TOML file it ignores `.conf` files, so a stray `flyway.toml` can silently disable an older `flyway.conf` project. Naming both a `.conf` and a `.toml` file in `-configFiles` is an error. Convert an older project with `flyway init -fromType=Conf`. Flyway Desktop also upgrades a `.conf` project to TOML when you open it from the landing page, and keeps a backup (from Desktop 8.4.1). Desktop can upgrade a project with deprecated configuration automatically when it opens, and lists the changes it made from Desktop 9.4.3. When a value isn't what you expect, run the command with `-X` (debug output).

`-workingDirectory` is the base for relative paths, including `locations`, `configFiles`, `filterFile`, `rulesLocation`, `rulesConfig`, report and dry-run output paths and snapshot file names, and for finding the config files. It has no environment variable. Pass it, or run from the project folder.

Command-line options worth knowing:

| Option | Does |
|---|---|
| `-outputType=json` | JSON to standard output; errors go in the JSON payload instead of standard error |
| `-outputLogsInJson` | With `-outputType=json`, standard logs are JSON too |
| `-outputFile=<path>` | Also writes console output to a file |
| `-q` | Quiet: errors and warnings only |
| `-color=always`, `never` or `auto` | Colored output; default `auto` |
| `-X` | Debug output |

Namespaced settings on the command line. The full form, such as `-check.buildEnvironment=build`, always works. The short form (`-buildEnvironment=build`) works only directly after its verb, not when placed before the verb, and not for a later verb in a chain (`flyway diff generate -diff.source=...` needs the namespace). Use the full form in scripts for consistency, and quote it in PowerShell, which can split arguments that contain a dot: `"-check.buildEnvironment=build"`.

Documentation: https://documentation.red-gate.com/fd/configuration-precedence-277578840.html

## 2. Anatomy of flyway.toml

| Section | Holds | Who edits it |
|---|---|---|
| Root keys `id`, `name`, `databaseType` | Project identity | Written by Desktop or `flyway init`; leave alone |
| `[environments.<name>]` | `url`, `user`, `password`, `schemas`, `provisioner`, `jdbcProperties`, and resolvers under `[environments.<name>.resolvers.<resolver>]` | DBAs |
| `[flyway]` and namespaces such as `[flyway.generate]`, `[flyway.placeholders]` | Locations, validation, history table, generation | DBAs, by pull request |
| `[flywayDesktop]` | Which environments Desktop uses as development and shadow | Written by Desktop |
| `[redgateCompare.sqlserver]`, `[[redgateCompare.staticDataTables]]` | `filterFile`, comparison `options.behavior` and `options.ignores`; static data tables | DBAs, by pull request |

The `[flywayDesktop]` keys are `developmentEnvironment` and `shadowEnvironment`. That's what `flyway init` writes, and what Redgate's Flyway MCP server page (preview) and Enable migrations tutorial show. The Desktop namespace reference pages list `development` and `shadow` instead; don't copy those. If a working file already has keys, leave them. If Desktop asks for connection details on opening the project, a key's value doesn't match an environment name.

Other `[flywayDesktop]` details:

- `[flywayDesktop] schemaModel` is deprecated. Use `[flyway] schemaModelLocation`.
- `[flywayDesktop.generate]` holds Desktop-only generation settings: `undoScripts` (default `false`) and `repeatableTypes` (default `[]`). They don't change what the command line generates; that's `[flyway.generate] types`.
- `[flywayDesktop] showDeploymentDecision` defaults to `false`, but new projects get `true`.

`flyway init` and Desktop write `outOfOrder = true` and `mixed = true` even though the engine defaults are `false`. Read your own file (file 09 covers `outOfOrder`). Add `flyway.user.toml` to `.gitignore`; a pipeline credential never lives there.

Environment and history settings worth knowing:

- `connectRetries` defaults to `0`; `connectRetriesInterval` defaults to `120` seconds.
- `initSql` is deprecated. Use an `afterConnect` SQL callback instead; it runs reliably on the migration connection from engine 13.1.0.
- `callbackLocations` has no default (`flyway init` adds `filesystem:callbacks`). If it isn't set, Flyway scans `locations` for callbacks. `deploy` reads callbacks only from `callbackLocations`, so a state-based project that relies on callbacks must set it.
- SQL callback files are named after the event they handle, for example `afterConnect.sql`, `beforeMigrate.sql`, `afterMigrate.sql`, `afterClean.sql` and `beforeDeploy.sql`. A file whose name doesn't match an event, or that sits outside the callback location, never runs. Callbacks fire on every command that raises the event, not only on `migrate`, so write them to be safe to run again.
- `communityDBSupportEnabled` defaults to `true`. Set it to `false` to block connections to community-supported databases.
- `schemas` is case-sensitive. When `defaultSchema` isn't set, the first entry is the default schema and holds the schema history table. With `createSchemas = false`, each schema must already exist. On SQL Server, `schemas` is ignored by `diff` and `prepare` (section 9), and it can't be combined with some clean modes (section 5).
- Changing `table` makes Flyway look for a different schema history table, so on a database that already has history it looks like an unmigrated one. Don't change it once a project has deployed.

Documentation: https://documentation.red-gate.com/flyway/reference/configuration/flyway-desktop-namespace

## 3. Recognizing a fresh project vs a configured one

A `flyway.toml` existing doesn't mean a team has set Flyway up. `flyway init` and Desktop's new-project flow write a complete-looking file in seconds. Redgate's Init command page says only that `init` "generates a new Flyway project, complete with recommended files and configuration for a given database type". Redgate's own command-line workbook shows what that means for SQL Server:

- Root keys `databaseType`, `name` and a generated `id`.
- `[flyway]` with `locations = [ "filesystem:migrations" ]`, `mixed = true`, `outOfOrder = true` and `schemaModelLocation = "schema-model"`. Other non-default values, such as `validateMigrationNaming`, depend on the version that created the project, so read the file rather than a list.
- `[flywayDesktop]` with `developmentEnvironment = "development"` and `shadowEnvironment = "shadow"`.
- An empty `migrations/` folder, an empty `schema-model/` folder, a default `Filter.scpf` and a `.gitignore`.
- No `[environments.*]` tables. The workbook says "By default, no database connections are configured".

Desktop adds development and shadow connections when someone links a database, by default in the git-ignored `flyway.user.toml`, so a committed file can look empty even on a developer's working copy.

Redgate also publishes sample projects (the Autopilot templates) whose `flyway.toml` defines `development`, `shadow`, `Build`, `Check`, `Test` and `Prod`, all pointing at `localhost` sample databases with `integratedSecurity=true`, `trustServerCertificate=true` and `baselineOnMigrate = true`, plus example migrations. A file shaped like that is a copied template, not a configured estate.

| Signal | Fresh or template | Configured and in use |
|---|---|---|
| `[environments.*]` | None, only `development` and `shadow`, or `localhost` sample names | Real targets through placeholders and `${env.X}`, or `ci/<environment>.toml` files |
| `migrations/` | Empty, or only sample scripts | A baseline (`B`) script or a chain of versioned scripts with team ticket keys |
| `schema-model/` | Empty | Object folders matching your database |
| `Filter.scpf` | Unchanged default | Edited, committed, reviewed |
| Settings | `mixed`, `outOfOrder` and `baselineOnMigrate` exactly as generated | Values someone changed deliberately, with a reason in the pull request or decision log |
| Pipeline | No `.github/workflows/` using Flyway | Workflows that pass `-environment=` for each deployed environment (and load any `ci/` files) |
| Git history | One "initial" commit | Commits from several people over time |
| Targets | `flyway info` shows no schema history table | `flyway info` shows applied migrations |

What the assistant does with this:

- Treat a fresh or template project as a starting point. Don't describe environments, baselines, approvals or pipelines as existing because the file mentions them.
- Before advising on a generated setting, say it was written by the generator, not chosen: `outOfOrder = true` and `mixed = true` are the usual examples (file 09, and section 11 of this file).
- Ask before assuming a `localhost` URL, a sample database name or `trustServerCertificate=true` is intentional.
- For a configured project, read its settings as decisions and change them only by pull request.

## 4. JDBC URLs: on-premises SQL Server and Azure SQL

On-premises forms (`<server>`, `<db-name>`):

| Case | URL |
|---|---|
| Default instance | `jdbc:sqlserver://<server>:1433;databaseName=<db-name>;encrypt=true` |
| Named instance | `jdbc:sqlserver://<server>;instanceName=<instance>;databaseName=<db-name>;encrypt=true` |
| Named instance, fixed port | `jdbc:sqlserver://<server>:<port>;databaseName=<db-name>;encrypt=true` |
| Windows authentication | add `integratedSecurity=true` and omit `user` and `password` |

- A named instance without a port relies on the SQL Server Browser service. Where it's blocked, use the fixed port (with both, the driver uses the port).
- Set `encrypt=true`, use a certificate the runner trusts, and leave `trustServerCertificate` unset. `true` skips validation, so limit it to private development networks and record it in your decision log (file 01).
- `integratedSecurity=true` on Windows needs the driver's `mssql-jdbc_auth` DLL. The Windows command-line package carries it in its `native` folder, and Redgate's Windows authentication tutorial needs no extra steps. Linux runners use Kerberos (`authenticationScheme=JavaKerberos`, Redgate's Kerberos tutorial). Set `[flyway] kerberosConfigFile` (the `krb5.conf` path) and pair it with `[flyway.sqlserver] kerberos.login.file` (the `SQLJDBCDriver.conf` path); Desktop takes these settings only through TOML.
- LocalDB: the Microsoft driver doesn't support LocalDB named pipes. Redgate's Local DB resolver, `${localdb.pipeName}` with `instanceName` under `[environments.<name>.resolvers.localdb]`, finds the pipe name, which changes on restart. It works with the jTDS driver only. jTDS doesn't accept `localhost` (use `.`), Windows authentication through jTDS needs `ntlmauth.dll`, and `SET ANSI_NULLS` or `SET QUOTED_IDENTIFIER` in a script errors with jTDS.

Azure SQL. This library covers both Azure SQL Database and Azure SQL Managed Instance, and an estate can hold both. The same driver settings and Entra options apply to each; the host differs, so the host name tells you which one a URL points at. A Managed Instance's VNet-local endpoint is reached from inside the network, which usually means a self-hosted runner (file 12):

| Service | Host and port |
|---|---|
| Azure SQL Database | `<azure-sql-server>.database.windows.net`, port 1433 |
| Managed Instance, VNet-local endpoint | `<mi-name>.<dns-zone>.database.windows.net`, port 1433 |
| Managed Instance, public endpoint (if enabled) | `<mi-name>.public.<dns-zone>.database.windows.net`, port 3342 |

> Not from Redgate docs — starting point, validate in your environment.

```text
jdbc:sqlserver://<azure-sql-server>.database.windows.net:1433;databaseName=<db-name>;encrypt=true
```

Add `authentication=<value>` to choose how the driver signs in with Microsoft Entra. Floors are Microsoft JDBC driver versions, from Microsoft Learn:

| Value | Use | Driver floor and notes |
|---|---|---|
| `ActiveDirectoryServicePrincipal` | Pipeline service principal (in Redgate's Entra tutorial) | 9.2. `user` is `<client-id>`, `password` the secret |
| `ActiveDirectoryServicePrincipalCertificate` | Service principal with a certificate | 12.4 |
| `ActiveDirectoryMSI` | Self-hosted runner on Azure with a managed identity (in Redgate's tutorial) | 7.2. `msiClientId=<client-id>` for a user-assigned identity. Newer name `ActiveDirectoryManagedIdentity`, 12.2 |
| `ActiveDirectoryDefault` | Whatever the Azure credential chain finds (environment variables, managed identity, Azure CLI sign-in) | 12.2. A Microsoft driver mode Redgate's tutorials don't cover: prove it in your POC before a pipeline depends on it |
| `ActiveDirectoryInteractive` | Developer browser sign-in | 9.2. Prompts on every call without the resolver below |
| `ActiveDirectoryIntegrated` | Domain-joined machine federated with Entra | 6.0. Auth DLL or Kerberos |
| `ActiveDirectoryPassword` | Entra user and password | Deprecated by Microsoft; fails where MFA is enforced |

The command line ships the Microsoft driver plus Microsoft's `azure-identity` and `msal4j` libraries, so no extra jars are needed for these modes. Redgate's engine release notes record the driver upgrade to `mssql-jdbc` 12.10.2 in engine 11.16.0, which clears every floor in the table; file 25 records what was checked. Confirm on your own install by looking at the `mssql-jdbc-<version>.jar` in the `drivers` folder, then run `flyway testConnection -environment=<env>`, which tests Flyway's and the comparison engine's connections.

Redgate documents four Entra routes for SQL Server: service principal, managed identity (`ActiveDirectoryMSI`), interactive sign-in through the Entra resolver, and an access token fetched with `az account get-access-token`. Start with one of those. Redgate's docs call managed identity the most secure option, because there's no secret at all; it needs a runner on Azure.

For developer machines, the Microsoft Entra Interactive resolver caches the token. It needs `tenantId` and `clientId`. `entraId` is an alias for the older `azureAdInteractive` resolver name (from engine 12.0.1); write `entraId`:

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.development]
url = "jdbc:sqlserver://<azure-sql-server>.database.windows.net:1433;databaseName=<db-name>;encrypt=true"

[environments.development.jdbcProperties]
accessToken = "${entraId.token}"

[environments.development.resolvers.entraId]
tenantId = "<tenant-id>"
clientId = "<client-id>"
```

The resolver needs an Entra app registration with the redirect URIs `https://login.microsoftonline.com/common/oauth2/nativeclient` and `http://localhost`, and the delegated `user_impersonation` permission on Azure SQL Database. Without the resolver, Desktop prompts you to sign in on every connection.

For pipelines, Redgate's Entra tutorial also documents an access token in `jdbcProperties.accessToken` (section 7): https://documentation.red-gate.com/fd/tutorial-connect-using-microsoft-entra-id-339477241.html

## 5. The six environments

| Environment | What it is | Defined in | Provisioner | Connects as |
|---|---|---|---|---|
| `development` | A developer's own database (file 08) | `flyway.toml`, no credentials | None | Developer role |
| `shadow` | Flyway's throwaway comparison database | `flyway.toml` | `clean` | Developer role |
| `build` | CI throwaway for proving migrations and the schema model | `flyway.toml`, credentials through `${env.X}` | `clean` | Deploy account on a build server |
| `test` | Shared test database | `flyway.toml`, credentials through `${env.X}` | None, ever | Deploy account to deploy; read-only check account for `info` |
| `uat` | Pre-production | `flyway.toml`, credentials through `${env.X}` | None, ever | Same |
| `production` | Production | `flyway.toml`, credentials through `${env.X}` | None, ever | Same, behind approval |

Any deployed environment can live in an optional `ci/<environment>.toml` instead (section 6).

The admin role creates databases, logins and the accounts above. It isn't used by Flyway in any pipeline.

- On SQL Server the shadow is a separate database, not a schema. Each developer who generates migrations needs their own, on a non-production server.
- Run shadow and build databases on the same SQL Server major version as production (for example 2019 against 2022), or change reports show spurious differences. If they run in containers, pin the image tag rather than `latest` so reports are reproducible (file 16).
- The `clean` provisioner re-provisions an existing database by cleaning it; it can't create one. The other provisioners are (preview), and file 16 covers them and Azure SQL.
- Never give a long-lived database a provisioner. Provisioning runs before any command connects.
- To force a re-provision for one run, pass `-provisionMode=reprovision` on the command line. Don't write `provisionMode` in TOML.
- If build or shadow databases hold objects in several schemas, check what `clean` drops. On SQL Server, `[flyway.sqlserver.clean] mode` controls it, set in TOML (Redgate's SQL Server Clean Namespace page):

| `mode` | Drops |
|---|---|
| `default` | Used when `mode` isn't set |
| `schema` | All schemas that aren't built in |
| `all` | Everything, including schemas, non-fixed roles, keys, fulltext stoplists and XML schema collections |

- `[flyway.sqlserver.clean] schemas.exclude` protects named schemas when `mode = "all"`.
- Setting `mode` to `schema` or `all` while the environment also sets `schemas` is an error.
- Clean never drops users.
- From engine 13.10.0, a fix stops SQL Server clean mode configuration failing operations on databases that don't support clean mode. Pin 13.10.0 or later if you set `mode`.
- This sandbox's `flyway.toml` sets `mode = "all"`, so its shadow and build databases lose roles and schemas too. Point clean only at disposable databases.
- Never set `[flyway] environment` to a deployed environment. Workflows pass `-environment=` every time.

Documentation: https://documentation.red-gate.com/flyway/flyway-concepts/environments/shadow-and-build-environments

## 6. One shared file for every environment, and optional ci files

Current engines resolve `${env.X}` only for the environment a command uses. An unset variable in an environment the command doesn't use doesn't fail the command. Redgate's docs don't state this; it was tested. When the environment the command does use names an unset variable, the command fails with:

```text
Unable to resolve environment variable: '<NAME>'
```

So one shared `flyway.toml` can hold every environment. Each environment reads its own `${env.X}` names, and each step maps only its own environment's secrets and passes `-environment=<env>`. Developers and Desktop working against `development` and `shadow` don't need the deployed environments' variables.

Not tested: placeholders and `[flyway]`-level settings (outside any environment) that reference an unset variable. Treat those as resolved on every command: map their variables into every step, or prove otherwise on your pinned engine.

> Not from Redgate docs — starting point, validate in your environment.

```toml
# flyway.toml - committed, no credentials; the step that targets uat supplies them
[environments.uat]
url = "${env.FLYWAY_UAT_URL}"
user = "${env.FLYWAY_UAT_USER}"
password = "${env.FLYWAY_UAT_PASSWORD}"
```

> Not from Redgate docs — starting point, validate in your environment.

```powershell
flyway info -environment=uat
```

Optional: one `ci/<environment>.toml` per deployed environment. You no longer need these for `${env.X}` to resolve, but they're still a valid pattern when you want each job's secrets and targets scoped to that job. With this pattern each deployed environment lives only in its own file, so a `uat` job that loads `ci/uat.toml` and is passed a mistyped `-environment=production` fails with `Environment 'production' not found` instead of connecting. Because `-configFiles` adds to the automatically loaded files (section 1), the shared `flyway.toml` still applies; don't define the same environment in both.

> Not from Redgate docs — starting point, validate in your environment.

```powershell
flyway info -configFiles=ci/uat.toml -environment=uat
```

- Give each environment its own variable names, so a test secret mapped into a production step fails to resolve instead of connecting. A read-only check step and a deploy step map different secrets into the same names, so one environment definition serves both.
- `${env.X}` works in all Flyway configuration parameters from engine 12.6.2, including files loaded with `-configFiles`. Redgate's resolver page names Flyway namespace parameters and environment properties; whether it also covers other namespaces, such as `check` or `redgateCompare`, isn't stated.
- The fallback needs no resolver. Redgate's Environments Namespace page documents setting any environment setting from a variable named `environments_<environment>_<setting>`, for example `environments_uat_password`, with one more underscore per nested level (`environments_uat_jdbcProperties_accessToken`). The `environments_` prefix is case-insensitive, but `jdbcProperties` keys pass to the driver verbatim, so keep their casing. Use letters, digits and underscores in environment names.
- `FLYWAY_URL`, `FLYWAY_USER` and `FLYWAY_PASSWORD` are the legacy root settings. Flyway maps them to an environment named `default`, so they don't configure `uat`.

Documentation: https://documentation.red-gate.com/fd/environments-namespace-277578909.html

## 7. Secrets: environment variables, GitHub secrets and resolvers

No password, token, permit or credential-bearing URL goes in a committed file, a workflow log or an AI chat.

In order of preference:

1. No stored secret: a managed identity on a self-hosted runner, OIDC to Azure for an access token, or OIDC followed by the Azure Key Vault resolver (below). On-premises, Windows integrated authentication or Kerberos under the runner's service account (file 12).
2. GitHub environment secrets, one environment per target (`test`, `uat`, `production`). They reach only jobs that name the environment, and for `production` only after required reviewers approve.
3. Repository secrets for values every job needs, such as `FLYWAY_EMAIL` and `FLYWAY_TOKEN` for a service account. Air-gapped runners use `FLYWAY_OFFLINE_PERMIT_PATH`. Never write a license key.

A step maps secrets into its environment, and the environment's `${env.X}` references in `flyway.toml` (or its optional `ci/` file) read them:

> Not from Redgate docs — starting point, validate in your environment.

```yaml
      - name: Deploy to uat
        env:
          FLYWAY_EMAIL: ${{ secrets.FLYWAY_EMAIL }}
          FLYWAY_TOKEN: ${{ secrets.FLYWAY_TOKEN }}
          FLYWAY_UAT_URL: ${{ secrets.FLYWAY_UAT_URL }}
          FLYWAY_UAT_USER: ${{ secrets.FLYWAY_UAT_USER }}
          FLYWAY_UAT_PASSWORD: ${{ secrets.FLYWAY_UAT_PASSWORD }}
        run: flyway migrate -environment=uat
```

The job carries `environment: uat` (file 12 has the whole shape). Fork pull requests receive no secrets.

For Azure SQL without a stored database secret, sign in with `azure/login` using OIDC, fetch a token and map it to the access token property:

> Not from Redgate docs — starting point, validate in your environment.

```yaml
      - uses: azure/login@v3
        with:
          client-id: <client-id>
          tenant-id: <tenant-id>
          subscription-id: ${{ vars.AZURE_SUBSCRIPTION_ID }}
      - name: Get SQL token
        shell: bash
        run: |
          TOKEN=$(az account get-access-token --resource https://database.windows.net/ --query accessToken -o tsv)
          echo "::add-mask::$TOKEN"
          echo "environments_uat_jdbcProperties_accessToken=$TOKEN" >> "$GITHUB_ENV"
```

The token command is from Redgate's Entra tutorial; the variable follows the documented form (section 6). Keep `shell: bash` on Windows runners, whose default shell is PowerShell. On this path the `uat` environment carries no `user` or `password`: every `${env.X}` in the environment a command uses must resolve, and this step maps no user or password. The identity needs a database user (`CREATE USER [<app-name>] FROM EXTERNAL PROVIDER`) with the deploy role.

Resolvers fetch values at run time, using `${resolver.key}` and configured under `[environments.<name>.resolvers.<resolver>]`. Use only resolvers on Redgate's Environment Resolvers Namespace page. Relevant here: Environment Variable (`${env.X}`), Azure Key Vault, Microsoft Entra Interactive, Git, Local Secret, Local DB (LocalDB only, section 4) and Placeholder (`${placeholder.NAME}`, section 8).

On developer machines, `flyway.user.toml` keeps connection details out of Git, but it isn't encrypted. Only operating-system file permissions protect it, and a script callback running as that user can read it. Describe it to your security team as "not committed", never as secure storage. Prefer Windows authentication or Entra for development connections, and where a password can't be avoided, use the Local Secret resolver instead of writing the password into the file.

The Azure Key Vault resolver (Flyway Enterprise, from engine 12.5.0) takes one setting, `vaultUrl`. Desktop honors it but can't set it. Redgate prefers this per-environment resolver to the older global `[flyway.akv]` settings:

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.uat.resolvers.azureKeyVault]
vaultUrl = "https://<vault-name>.vault.azure.net"

[environments.uat]
password = "${azureKeyVault.<secret-name>}"
```

What's documented and what to prove:

- How the resolver signs in to Key Vault: Redgate's resolver page documents the settings, not the sign-in. Flyway is expected to use the Azure SDK's standard credential chain, the same one other Azure tools use, through the `azure-identity` library the command line bundles. If so, it takes whichever identity the runner has: a service principal through the `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_CLIENT_SECRET` environment variables, a workload identity, a managed identity on a self-hosted runner in Azure, or an Azure CLI sign-in. An `azure/login` step in GitHub Actions leaves an Azure CLI sign-in, which the resolver is expected to honor, so `azure/login` with OIDC followed by the resolver would need no stored vault secret. Prove it: read one test secret with your runner's exact identity in your proof of concept before a pipeline depends on it.
- Permission, from Microsoft's Key Vault docs: the **Key Vault Secrets User** role on vaults using Azure role-based access control, or the secret **Get** permission on vaults still using access policies. Grant it on the one vault, not the subscription; Microsoft recommends one vault per application per environment, with roles assigned at vault scope.
- Use the resolver for environment connection settings (`url`, `user`, `password`), which is where Redgate documents it. Don't rely on it inside `[flyway.placeholders]` without proving it.
- If the resolver doesn't fit your security model, the fallback is `azure/login` plus a step that reads the secret (`az keyvault secret show`) into a masked variable and passes it as `${env.X}`.

Always write environment variables as `${env.X}`. A few Redgate pages show `${FLYWAY_PASSWORD}` without `env.`; the Environment Variable resolver page documents the `env.` form.

Resolvers can't be nested, and a resolver that depends on another must be configured after it. To stop a stray value injecting characters, add a filter: `${resolver.key:AD}` keeps letters and digits, `:ad` keeps ASCII letters and digits only. Escape a literal `${...}` as `$${...}`, or wrap the whole value in `!{ ... }` to stop Flyway resolving anything in it.

Never put a secret in `[flyway.placeholders]`. Placeholder values end up in the SQL that runs, and Redgate's pages show resolvers configured only inside environments.

Documentation: https://documentation.red-gate.com/fd/environment-resolvers-namespace-277578931.html

## 8. Placeholders

Placeholders replace `${key}` in versioned and repeatable migrations and SQL callbacks.

> Not from Redgate docs — starting point, validate in your environment.

```toml
[flyway.placeholders]
reportingRole = "<reporting-role>"
```

- Command line: `-placeholders.reportingRole=<value>`. Environment variable: `FLYWAY_PLACEHOLDERS_<KEY>`.
- Built-in: `${flyway:defaultSchema}`, `${flyway:user}`, `${flyway:database}`, `${flyway:environment}`, `${flyway:timestamp}`, `${flyway:filename}`, `${flyway:workingDirectory}` and `${flyway:table}`.
- Redgate's docs: changing a placeholder value re-applies repeatable migrations on the next `migrate`.
- Placeholders aren't documented for state-based deployment scripts (`prepare` and `deploy` from the schema model). Don't rely on them there.
- Use them for values that differ per environment, such as a linked server name.
- `placeholderReplacement` defaults to `true`. `placeholderPrefix`, `placeholderSuffix` and `placeholderSeparator` default to `${`, `}` and `:`.
- The Placeholder resolver, `${placeholder.NAME}`, reads values from `[flyway.placeholders]` into other configuration. It covers user placeholders only, not the `${flyway:...}` built-ins.

When a migration fails with `No value provided for placeholder: ${<name>}.  Check your configuration!`, there are three usual causes:

1. The placeholder isn't defined for this environment. Define it in `[flyway.placeholders]` or `[environments.<env>.flyway.placeholders]`.
2. SQL text that only looks like a placeholder, such as `${...}` inside dynamic SQL or JSON.
3. SQLCMD `$(var)` variables in scripts brought over from SQL Change Automation or SQL Source Control. They aren't Flyway placeholders.

For the last two, stop Flyway replacing the text: turn replacement off (`placeholderReplacement = false`, or in a per-script config for just that script), or change `placeholderPrefix` and `placeholderSuffix` to something the scripts never contain. `-X` shows the effective configuration and, from engine 13.5.0, where each value came from.

## 9. Filters and SQL Server comparison options

The filter file removes objects Flyway doesn't own from capture, generation, `prepare`, change reports and drift checks. On SQL Server it's a SQL Compare filter, `Filter.scpf` (resolved relative to the working directory) by default, or the path in `[redgateCompare.sqlserver] filterFile`, which also takes `-redgateCompare.sqlserver.filterFile=` for one run. By default Flyway already filters out users and objects holding secure information, such as certificates. Don't use the generic `[redgateCompare] filterFile` for SQL Server. From engine 13.9.0, `flyway init` no longer writes that root key for SQL Server projects. A leftover one, such as `filterFile = "filter.rgf"` in this sandbox's `flyway.toml`, is harmless while `[redgateCompare.sqlserver] filterFile` is set, and you can remove it. File 09 has a team-scoping filter example.

- Filters apply after comparison, so they don't speed it up, and a filtered object can still be pulled into a script as a dependency.
- On SQL Server the environment `schemas` setting is ignored by `diff` and `prepare`, and Desktop says not to set it. The filter is the scope.
- Edit in Desktop's filter editor, or SQL Compare's for complex rules, and commit the result. Filter objects another system manages, and scratch objects by naming convention.
- In `Filter.scpf`, the `None` node sets the default for object types. Expressions that Desktop's filter editor doesn't support, for example from an imported `Filter.scpf`, show read-only there; change those in SQL Compare or by hand.

Comparison options live under `[redgateCompare.sqlserver.options.behavior]` and `[redgateCompare.sqlserver.options.ignores]`. Settings in `ignores` are booleans named for what they ignore, such as `ignoreWhiteSpace`, `ignoreComments` and `ignorePermissions`. Behavior options are booleans too, mostly `false` by default, for example `addObjectExistenceChecks` and `addOnlineOnWhenCreatingIndexesOrAlteringColumns`. Redgate documents each option on its own page, so look an option up there before you set it. In Desktop, set them on the Schema model tab under Static data & comparisons. From Desktop 9.4.3, SQL Server static data deployment can add existence checks to INSERT statements.

Two ignores catch out most teams on their first capture, and both ship as `false` in this sandbox template:
- `ignoreSystemNamedConstraintAndIndexNames`. A constraint or index created without a name gets one generated by SQL Server, such as `DF__Orders__Creat__19B5BC39` or `PK__Orders__F2AF558AE9CD66`, and the suffix is different in every database. With this option off, Flyway reports the same table as changed between environments when only that generated name differs. Turn it on to stop the noise. The long-term fix is to name constraints explicitly.
- `ignorePermissions`. Object-level `GRANT`, `DENY` and `REVOKE` statements on tables, views and procedures are captured into the schema model and migrations while this is off. Most teams manage permissions per environment outside Flyway, so they turn it on. It's separate from `ignoreUsersPermissionsAndRoleMemberships`, which covers users and role memberships (the template already sets that to `true`).
After changing either option, refresh the comparison. Already-applied migrations aren't changed. Check the schema model diff before committing, in case objects captured earlier still need tidying.

`[flyway.diff] includeFlywayObjects` defaults to `false`.

`[redgateCompare.sqlserver.options.behavior] includeDependencies` defaults to `true`. It pulls dependent objects into schema model saves, generated migrations and deployment scripts, and Desktop shows a dependency review step. `false` turns it off.

> Not from Redgate docs — starting point, validate in your environment.

```toml
[redgateCompare.sqlserver.options.ignores]
ignoreWhiteSpace = true
```

Flyway fixes some options that SQL Compare lets you change: it always compares check constraints, keys, constraint names, identity properties and trigger order, and generates scripts without transactions or error handling. That explains most "SQL Compare shows a difference Flyway doesn't" questions (file 19). Each ignore hides real drift, so make each one a recorded decision. Redgate's `prepare` page says options and static data are read only from TOML, not the command line.

Documentation: https://documentation.red-gate.com/flyway/reference/configuration/redgate-compare-namespace/redgate-compare-sql-server-namespace

## 10. Per-environment overrides, and the 13.10.0 note

A `flyway` table inside an environment overrides root `[flyway]` settings for that environment only. An overridden key replaces the root value in full (a `locations` list isn't merged with the root list); keys you don't set keep their root value:

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.test.flyway]
locations = ["filesystem:migrations", "filesystem:migrations-test"]
```

What Redgate's Environment Overrides page says can and can't be overridden:

- Only `environment` itself can't be overridden.
- `email`, `token` and the license key can be, but Redgate doesn't recommend it. Keep licensing values out of `flyway.toml` altogether and pass them as environment variables (file 04).
- Other namespaces, such as `check`, can be overridden too. The engine 13.10.0 release note added `undoSqlMigrationPrefix` and `check.buildEnvironment`, so treat 13.10.0 as the floor for overrides outside the core `flyway` settings. An unknown key is an error.
- Command-line-only settings can't be set per environment: the working directory, config files, config file encoding, output type and color.
- Environment overrides have no dedicated environment variable support. The command-line form is `-environments.<env>.flyway.<setting>=<value>`.

`cherryPick` isn't named on the exclusion list, so it's probably allowed, but keep it on the command line anyway (below). Older copies of the environment Flyway namespace page listed more exclusions; it now links to the overrides page. Prove an override on your pinned engine before a pipeline depends on it, with a run whose result shows the overridden behavior. Don't rely on `-X` to show where a value came from.

> Not from Redgate docs — starting point, validate in your environment.

```toml
[environments.uat.flyway]
check.buildEnvironment = "build"
```

Keep per-run choices such as `cherryPick` and `target` on the command line, never in `flyway.toml` or a `ci/` file.

The same sub-table turns Flyway Insights (preview) on for chosen environments only: `publishResult = false` under `[flyway]` and `publishResult = true` under `[environments.<name>.flyway]`, on an engine later than 13.10.0, proven on your version (file 18, section 7).

Documentation: https://documentation.red-gate.com/fd/environment-overrides-295176010.html

## 11. Safety settings worth writing down

| Setting | Value | Why |
|---|---|---|
| `cleanDisabled` | `true` | The default. Writing it makes the intent reviewable. Clean only build, shadow or scratch databases |
| `validateMigrationNaming` | `true` | Default `false`, which skips misnamed files |
| `failOnMissingLocations` | `true` | Default `false`; a mistyped location builds a smaller schema and reports success |
| `outOfOrder` | `false` on shared environments (the strict stance), or `true` everywhere only if the project chose the permissive stance with its two-order build | File 09, section 5 |
| `mixed` | `false` | `flyway init` writes `true` |
| `installedBy` | The workflow run ID, passed on the command | History rows trace to a run |
| `saveSnapshot` | `true` on deployed runs, on the command line | Default `false` on the CLI; drift checks need it (file 14) |

Repair is never automated: a person runs `repair` after reading `info`. Production runs from an on-demand workflow behind approval (file 11).

## 12. A complete example: flyway.toml

> Not from Redgate docs — starting point, validate in your environment.

```toml
# flyway.toml - committed, no credentials
id = "<written by Desktop>"
name = "<service name>"
databaseType = "SqlServer"

[flywayDesktop]
developmentEnvironment = "development"
shadowEnvironment = "shadow"

[flyway]
locations = ["filesystem:migrations"]
validateMigrationNaming = true
failOnMissingLocations = true
cleanDisabled = true
outOfOrder = false
mixed = false

[flyway.generate]
types = ["versioned", "undo"]
timestamp = "always"

[redgateCompare.sqlserver]
filterFile = "Filter.scpf"

[environments.development]
url = "jdbc:sqlserver://<server>:1433;databaseName=<db-name>_dev;encrypt=true;integratedSecurity=true"

[environments.shadow]
url = "jdbc:sqlserver://<server>:1433;databaseName=<db-name>_shadow;encrypt=true;integratedSecurity=true"
provisioner = "clean"

[environments.build]
url = "jdbc:sqlserver://<server>:1433;databaseName=<db-name>_build;encrypt=true"
user = "${env.FLYWAY_BUILD_USER}"
password = "${env.FLYWAY_BUILD_PASSWORD}"
provisioner = "clean"

[environments.uat]
url = "${env.FLYWAY_UAT_URL}"
user = "${env.FLYWAY_UAT_USER}"
password = "${env.FLYWAY_UAT_PASSWORD}"
```

`test` and `production` follow the `uat` shape with their own variable names. No credential is written in the committed file: each step maps only its own environment's variables, and an unset variable in an environment the step doesn't use doesn't fail it (section 6). Developers working on `development` and `shadow` need none of them. If you prefer per-environment files, move `build` and the deployed environments into `ci/<environment>.toml` files instead (section 6).

## 13. In daily use

DBAs change configuration by pull request, with code-owner review on `flyway.toml`, `ci/`, filters and `.github/workflows/`. Show the effect in the pull request: `flyway info -X -environment=<env>` against `test` (add `-configFiles=ci/<env>.toml` if you use the optional per-environment files), and a `flyway diff` if a filter changed. Nobody edits configuration on a runner. Record decisions in your decision log (file 01).

After a URL or credential change, run `flyway testConnection -environment=<env>`. It changes nothing and, unlike `info`, runs no callbacks or validation.

## 14. Limits

- The Azure Key Vault resolver is expected to sign in through the Azure SDK credential chain, but Redgate's resolver page doesn't describe how it signs in. Prove your runner's identity on a test secret before relying on it (section 7).
- `${env.X}` works in all Flyway configuration parameters from engine 12.6.2, including `-configFiles` TOMLs. Whether that covers namespaces other than `flyway` and environment properties isn't stated. The `environments_<env>_<setting>` variables are the documented fallback.
- That an unset `${env.X}` in an unused environment doesn't fail a command comes from testing, not from Redgate's docs. Placeholders and `[flyway]`-level settings that reference an unset variable weren't tested (section 6).
- That `-configFiles` adds to the automatically loaded files is on Redgate's configFiles page and was confirmed in testing, but the precedence page reads otherwise. Prove it on your engine (section 1).
- The SQL Server driver page doesn't state the bundled driver version; the engine release notes do (section 4). Check the `drivers` folder after each upgrade.
- What can be overridden per environment depends on the engine (widened in 13.10.0). Prove it.
- How a second config file overrides a table array, such as `[[redgateCompare.staticDataTables]]`, isn't documented.

## 15. Instructions for the AI assistant using this file

- Never write a password, token, permit, license key, credential-bearing URL or real host name into any file. Use `${env.X}` and the placeholders `<server>`, `<db-name>`, `<azure-sql-server>.database.windows.net`, `<tenant-id>` and `<client-id>`.
- Keep every environment in the shared `flyway.toml` by default, each with its own `${env.X}` names. Offer per-environment `ci/<environment>.toml` files only as an option for scoping secrets per job, never as a requirement.
- Before adding `${env.X}` to an environment, confirm every step that targets that environment maps the variable. Keep `${env.X}` out of placeholders and `[flyway]`-level settings unless every step maps it (that case is untested).
- When a command fails with `Unable to resolve environment variable: '<NAME>'`, the environment it targets names a variable the step didn't map.
- Never put `email`, `token` or a license key in `flyway.toml`, even as an environment override. Never set `[flyway] environment` to a deployed environment.
- Work out whether each target is on-premises SQL Server, Azure SQL Database or Managed Instance from its host name (section 4) or the discovery in file 01. If neither tells you, ask; never assume one for the whole estate.
- Before describing a project, check the section 3 signals. Never treat a freshly generated or template `flyway.toml` as evidence that environments, baselines or pipelines exist.
- Use only resolvers on Redgate's resolvers page (section 7). Never invent a resolver or a setting.
- Never enable clean outside build, shadow or scratch, and never add a provisioner to a shared environment.
- For any per-environment override outside the core `flyway` settings (13.10.0 floor), say it needs proving on the pinned engine with a run that shows the overridden behavior.
- In command examples, write namespaced settings in full and quote them for PowerShell (`"-check.buildEnvironment=build"`).
- When a setting isn't taking effect, ask for the command and its `-X` output first.
- For `[flywayDesktop]`, write `developmentEnvironment` and `shadowEnvironment`. If a working file already has keys, leave them.
- Mark composed files as composed, show the whole changed section, and point to file 12 for how a workflow loads it.
